# x86 基线：真实测量，但不是目标硬件

> [!WARNING]
> **这里的所有数字都来自一台 Intel Xeon 服务器，不是 RK3588。**
> 不要把它当成 RK3588 的预测值或上限。两者的 ISA、内存带宽、核数、
> 功耗预算全都差一个数量级以上。

## 这些数据是干什么用的

模型的 GGUF 转换和量化本来就要在一台有内存、有磁盘的机器上做（RK3588 的
4~16GB 内存装不下 BF16 中间产物：光 Qwen3-4B 的 BF16 就有 8.05 GB）。
既然模型已经在这台机器上了，顺手测一遍 llama.cpp，可以拿到三样东西：

1. **验证工具链是通的**——从 HF 权重到 GGUF 到量化到能吐出通顺的句子，
   整条链路走通了，说明后面上板时如果出问题，问题在板子那边而不在产物这边。
2. **验证量化产物没坏**——量化最容易出的问题是"能加载但输出是乱码"。
   每个模型都用 `llama-cli` 实际生成了一段文字做人工抽查。
3. **一个相对关系的对照组**——绝对 tok/s 没有可比性，但"Q4_K_M 比 Q8_0
   快多少倍"这种**比值**在两个平台上都有定义，而且它们的差异恰好能反过来
   验证本项目的核心论点（见下面的分析）。

它**不能**用来做的事：外推 RK3588 的 tok/s。

## 环境

见 [`sysinfo-x86.txt`](sysinfo-x86.txt)。要点：

| | x86 基线机 | RK3588（目标硬件） |
| --- | --- | --- |
| CPU | Xeon Platinum 8558P，2 socket × 48 核 | 4× A76 @2.4GHz + 4× A55 |
| int8 SIMD | AVX-512 + AVX512-VNNI | NEON dotprod（**无** i8mm/SVE） |
| 内存 | 2015 GiB，2 NUMA node，多通道 DDR5 | 4/8/16 GB 单通道 64-bit LPDDR4x |
| 标称带宽 | 数百 GB/s | 34.1 GB/s（实测通常 ~15 GB/s） |

**带宽差了大约 20 倍**——这是下面所有分析的关键。

## 方法

```bash
llama-bench -m <model>-Q4_K_M.gguf -m <model>-Q8_0.gguf \
            -p 512 -n 128 -t 4,8,16 -r 3 -o md
```

- `pp512` = prefill 512 token，`tg128` = decode 生成 128 token
- 每个配置重复 3 次，表里是 均值 ± 标准差
- 线程数取 4/8/16。**`-t 4` 是最有参照意义的一档**，因为 RK3588 能用来跑
  推理的大核就是 4 个（A55 小核加进去通常反而更慢，见 `docs/02-cpu-path.md`）

### 这批数据的可信度边界

- **机器是共享的**（采集时 load average 约 22，是宿主机上别的租户在跑）。
  同一个配置在不同时间采了三次，Qwen3-0.6B Q4_K_M `tg128` `-t 4` 分别得到
  **79.69 / 74.13 / 71.90 tok/s，极差 10.8%**——而每次运行自己报的标准差只有
  ±1.55。也就是说 `llama-bench` 的 `± sd` **只反映同一次运行内的抖动，
  严重低估了跨运行的真实不确定度**。
  所以：**三位有效数字不要当真**。下面的分析只依赖 1.3x~1.7x 这个量级的比值。
  表里保留原始小数位是为了忠实于工具输出，不代表精度。
- 没有绑核、没有控制 NUMA。`-t 16` 那一档尤其可能跨 socket。
- llama.cpp 自身的 `pp`/`tg` 定义与本仓库 `bench/metrics.py` 的
  prefill/decode 不完全等价（后者还测 TTFT 和 ITL 分位）。跨工具比较时注意。

## 结果

原始输出：[`bench-Qwen3-0.6B.md`](bench-Qwen3-0.6B.md)、
[`bench-Qwen3-1.7B.md`](bench-Qwen3-1.7B.md)、[`bench-Qwen3-4B.md`](bench-Qwen3-4B.md)。
下表是 `-t 4` 一档的汇总（完整的 4/8/16 线程数据在原始文件里）：

| 模型 | 量化 | 文件大小 | prefill pp512 (tok/s) | decode tg128 (tok/s) |
| --- | --- | ---: | ---: | ---: |
| Qwen3-0.6B | Q4_K_M | 456.11 MiB | 341.65 ± 12.64 | 71.90 ± 1.55 |
| Qwen3-0.6B | Q8_0 | 761.80 MiB | 254.27 ± 11.73 | 46.69 ± 1.34 |
| Qwen3-1.7B | Q4_K_M | 1.19 GiB | 138.31 ± 1.88 | 31.12 ± 0.02 |
| Qwen3-1.7B | Q8_0 | 2.01 GiB | 115.27 ± 0.02 | 20.34 ± 0.01 |
| Qwen3-4B | Q4_K_M | 2.32 GiB | 58.26 ± 2.75 | 11.81 ± 0.38 |
| Qwen3-4B | Q8_0 | 3.98 GiB | 45.27 ± 0.01 | 8.81 ± 0.00 |

三个模型都用 `llama-cli` 抽查过生成质量，输出通顺、语义正确，量化产物没有损坏。

### GGUF 里 embedding 存了两份（0.6B / 1.7B）

用 `gguf-py` 逐张量数了一遍元素总和：

| 模型 | 张量数 | token_embd | output.weight | 合计 |
| --- | ---: | ---: | --- | ---: |
| Qwen3-0.6B | 311 | 155.6M | **有，155.6M** | 0.752B |
| Qwen3-1.7B | 311 | 311.2M | **有，311.2M** | 2.032B |
| Qwen3-4B | 398 | 389.0M | 无（tied） | 4.022B |

三个模型的 `config.json` 写的都是 `tie_word_embeddings: true`，但转换出来
**只有 4B 真的共享了权重**，0.6B 和 1.7B 的 GGUF 里实实在在存了两份。

这不是统计口径的问题，是文件里真的有两份、要占两份 DRAM。对 4GB 的板子来说，
Qwen3-0.6B 平白多吃 100+ MB。**上板后如果内存吃紧，这是第一个该查的地方。**

## 分析：Q4_K_M 的加速为什么没达到体积比

decode 阶段如果是**纯内存带宽受限**，那么每 token 要读的字节数减半，
速度就该翻倍——也就是说：

```
decode 加速比（Q4_K_M / Q8_0）  应该等于  体积比（Q8_0 / Q4_K_M）
```

实测下来，加速比**无一例外地小于**体积比：

| 模型 | 线程 | 体积比 | decode 加速比 | 达成率 | Q4_K_M 有效带宽 | Q8_0 有效带宽 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 0.6B | 4 | 1.670 | 1.540 | 92.2% | 34.4 GB/s | 37.3 GB/s |
| 0.6B | 8 | 1.670 | 1.477 | 88.5% | 60.7 GB/s | 68.6 GB/s |
| 0.6B | 16 | 1.670 | 1.586 | 94.9% | 101.0 GB/s | 106.4 GB/s |
| 1.7B | 4 | 1.689 | 1.530 | 90.6% | 39.8 GB/s | 43.9 GB/s |
| 1.7B | 8 | 1.689 | 1.497 | 88.6% | 71.7 GB/s | 80.9 GB/s |
| 1.7B | 16 | 1.689 | 1.478 | 87.5% | 105.7 GB/s | 120.8 GB/s |
| 4B | 4 | 1.716 | 1.341 | 78.1% | 29.4 GB/s | 37.6 GB/s |
| 4B | 8 | 1.716 | 1.446 | 84.3% | 55.4 GB/s | 65.7 GB/s |
| 4B | 16 | 1.716 | 1.338 | 78.0% | 86.3 GB/s | 110.7 GB/s |

（有效带宽 = 权重字节数 × decode tok/s，即"每秒至少要过一遍的字节量"。
这是下界，没算 KV cache 和激活。）

两个观察，它们的**稳健程度不一样**，分开说：

1. **同一模型同一线程数下，Q8_0 的有效带宽永远高于 Q4_K_M——9 组配置无一例外**
   （4B `-t 16` 差到 86.3 vs 110.7 GB/s）。这是最硬的一条：Q4/Q8 是在同一次
   `llama-bench` 里前后脚测的，共享同样的机器状态，而且方向一致的 9/9
   即使按符号检验也只有 1/512 的概率是巧合，**不会被前面说的跨运行抖动翻盘**。
2. **达成率始终在 78%~95%，从没到过 100%。** 方向和第 1 条一致。不过要注意
   最高的 94.9% 离 100% 只差 5 个点，**小于 10.8% 的跨运行极差**，所以
   "个别配置能不能摸到 100%"这件事，这批数据其实答不了。
   能站住的是**总体没有一次超过 100%**，不是每一格的具体数值。

读得更少的那个反而没能把带宽吃满——多出来的时间花在**解量化**上了。
Q8_0 的解量化就是一个 int8 乘 scale；Q4_K_M 是 K-quant 超块结构，
scale/min 自己还是 6-bit 量化的，取一个权重要拆 nibble、还原两级 scale，
每字节要做的算术明显更多。带宽富裕的时候，这部分算术就成了新的瓶颈。

还要注意有效带宽随线程数一路涨到 100+ GB/s 也没有收敛——说明 `-t 4` 这一档
**离这台机器的内存墙还远得很**，此处根本不是带宽受限场景。这正是它跟 RK3588
最不像的地方，也是下面那条预测的依据。

### 没有成立的：达成率随模型增大而上升

先前只有 0.6B 和 1.7B 两个点时，看起来达成率随模型增大而上升（更接近带宽受限），
这本来会是支持核心论点的一个漂亮旁证。补上 4B 之后**这个趋势不成立**：
4B 反而是最差的一档（78%）。

而且就算趋势方向反过来算数，它也**站不住**：4B 的 78% 和 0.6B 的 92% 差 14 个点，
跟 10.8% 的跨运行极差是同一个量级。要判定模型大小和达成率之间到底有没有关系，
需要交替重复采样若干轮再看，这批数据做不到。

至于 4B 为什么偏低，可能与它是唯一 tied（没有独立 `output.weight`）因而张量
构成不同有关，也可能是更大工作集下的访存模式问题——两条都只是猜测，没有实验
支撑。**记为未解释现象，不写进结论。**

### 这对 RK3588 意味着什么

RK3588 的有效带宽大约是这台机器的 1/20，而它的解量化算力**没有**差 20 倍
（A76 有 dotprod，单核 int8 吞吐并不弱）。所以带宽那一侧会先撞墙，
解量化的开销会被藏在等内存的时间里。

**预测：RK3588 上 Q4_K_M / Q8_0 的 decode 达成率会显著高于 x86 上的 78%~95%，
应当更接近 100%（即加速比接近体积比 1.67~1.72x）。**

这条预测是可证伪的。上板后跑同样的 `llama-bench`：

- 达成率接近 100% → 支持"decode 受限于带宽"这一核心论点；
- 达成率反而更低 → 说明 A76 上 Q4_K_M 的解量化实现有性能问题
  （最可能是没走上 dotprod 路径），那就是 `kernels/` 里该动手的地方。

两种结果都有信息量，这正是先测 x86 的价值。

## 一个踩到的坑：`-st` 会把 `-no-cnv` 翻回去

抽查生成时用了 `llama-cli ... -no-cnv -st`，结果模型仍然套上了 chat template，
并且吐出了 `[Start thinking]` 开头的一大段思考内容。

原因是 `-st/--single-turn` 的语义是"**对话模式**只跑一轮"，它会重新打开
对话模式，覆盖掉前面的 `-no-cnv`。而 Qwen3 系列默认开启思考模式，一旦套上
chat template 就会先输出思考段落。

对 benchmark 来说这是致命的：TTFT 会变成"第一个思考 token 的时间"，
decode tok/s 里混进思考 token，整组指标失去意义。

**结论：纯补全场景只用 `-no-cnv`，不要加 `-st`。**
本仓库 `bench/backends/llama_cpp.py` 已按此处理并加了注释。

## 复现

模型转换/量化的完整命令记在服务器上的 `SETUP.md`，摘要：

```bash
source /path/to/EdgeLLM/env.sh
$EDGE_HF download Qwen/Qwen3-1.7B --local-dir models/Qwen3-1.7B
$EDGE_PY llama.cpp/convert_hf_to_gguf.py models/Qwen3-1.7B \
    --outfile gguf/Qwen3-1.7B-BF16.gguf --outtype bf16
llama-quantize gguf/Qwen3-1.7B-BF16.gguf gguf/Qwen3-1.7B-Q4_K_M.gguf Q4_K_M 16
llama-quantize gguf/Qwen3-1.7B-BF16.gguf gguf/Qwen3-1.7B-Q8_0.gguf   Q8_0   16
llama-bench -m gguf/Qwen3-1.7B-Q4_K_M.gguf -m gguf/Qwen3-1.7B-Q8_0.gguf \
    -p 512 -n 128 -t 4,8,16 -r 3 -o md
```

llama.cpp commit `4c6766fd7e4b5e8005ffde932c463bc494a33812`，
`-DGGML_NATIVE=ON -DLLAMA_CURL=OFF -DCMAKE_BUILD_TYPE=Release`。
