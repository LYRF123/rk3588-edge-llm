# Roofline：先知道天花板在哪

## 为什么先算再测

没有理论上限对照，「47 tok/s」这个数字既不能说明好也不能说明差。有了上限：

| 实测 / 上限 | 说明 |
| --- | --- |
| > 100% | **测量方法有问题**——多半是没数对 token，或被 cache 骗了 |
| 60% ~ 80% | 正常，运行时开销就这么多 |
| 30% ~ 60% | 有空间，值得挖 |
| < 30% | 有明显问题（没绑核？降频了？走了标量路径？） |

```bash
python3 -m bench roofline --model qwen2.5-1.5b-q4 --prompt-tokens 512
```

## 模型

对每个阶段分别算两个上限，取小的那个：

```
算力上限 = 有效算力(GOPS) / (参数量 × 2 ops)
带宽上限 = 有效带宽(GB/s) / 每 token 需读字节数
```

`× 2` 是因为每个权重参与 1 次乘 + 1 次加。

**每 token 需读字节数**在两个阶段完全不同：

- **prefill**：一次前向处理 N 个 token，权重读一遍被 N 个 token 摊薄
  → `权重字节 / N`
- **decode**：一次前向处理 1 个 token，权重读一遍只服务 1 个 token，
  还要加上整个 KV cache → `权重字节 + KV字节 × 上下文长度`

这个差别就是全部结论的来源。

## 算一遍：Qwen2.5-1.5B Q4

```
权重 = 1.54e9 参数 × 4 bit ÷ 8 × 1.125  ≈ 826 MiB
                                  └─ Q4_0 每 32 个权重带 1 个 fp16 scale，+12.5%

decode（上下文 512）：
  每 token 读 ≈ 840 MiB（权重 + KV）
  CPU 有效带宽 = 34.1 GB/s × 0.5 = 17 GB/s
  上限 = 17e9 / 840e6 ≈ 19.4 tok/s

  NPU 有效带宽 = 同样 17 GB/s（共享 DRAM）
  上限 = 19.4 tok/s   ← 一模一样

prefill（512 token 一批）：
  每 token 读 ≈ 840 MiB / 512 ≈ 1.6 MiB  → 带宽不再是瓶颈
  CPU 算力 = 614 GOPS × 0.6 = 368 GOPS → 368e9 / 3.08e9 ≈ 120 tok/s
  NPU 算力 = 6000 GOPS × 0.5 = 3000 GOPS → ≈ 974 tok/s   ← 8 倍
```

**这就是整个项目的核心论点：NPU 在 prefill 上有数量级优势，在 decode 上没有。**

## 效率系数从哪来

`efficiency_compute` 和 `efficiency_bandwidth` 是把标称值折算成可达值的系数。
默认值（0.6 / 0.5）是保守估计，**必须用实测覆盖**：

```bash
mbw -n 10 512        # 看 MEMCPY 那行，得到实测带宽
# efficiency_bandwidth = 实测带宽 / 34.1
```

然后改 `configs/models.yaml` 的 `hardware` 段。在这一步做完之前，
roofline 只是数量级参考，不是可信上限。

## 模型的局限

刻意做了简化，用的时候要知道：

- **不含 attention 的计算量。** 短上下文下占比很小，长上下文（>4K）下不可忽略。
- **不含 softmax / RMSNorm / RoPE 等 elementwise 算子。** 它们不吃算力但吃带宽。
- **假设权重每 token 完整读一遍。** 模型小到能进 cache 时不成立——
  但 RK3588 的 L3 只有几 MB，826 MiB 的模型不可能装下，所以这个假设是安全的。
- **不含运行时开销**（采样、tokenize、内存分配）。
- **embedding 全部计入。** 它在 decode 时不参与矩阵乘，但仍要查表占带宽；
  各模型 tie_word_embeddings 情况不同，这里保守地全算。

这些简化都会让上限**偏乐观**，也就是说实测低于上限是正常的，
高于上限一定是测量有问题。

## 突破上限的三条路

decode 卡在带宽上，靠优化算子是拿不回来的。真正有效的只有：

1. **减小模型** —— 1.5B → 0.5B，速度约 3 倍
2. **降低位宽** —— Q8 → Q4，速度约 2 倍（代价是精度）
3. **减少每 token 的读取量** —— 投机解码：一次前向验证多个 token，
   把权重读取摊薄。这是唯一不牺牲模型质量的路子。

第 3 条在端侧特别划算，因为端侧通常是单用户、batch=1，算力大量闲置。
用闲置算力换带宽是笔好买卖。这条还没进路线图，但值得做。
