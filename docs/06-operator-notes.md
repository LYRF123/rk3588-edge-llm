# 算子优化笔记

## 先说边界：能优化什么，不能优化什么

| 路径 | 能不能做算子优化 | 原因 |
| --- | --- | --- |
| **CPU（llama.cpp）** | ✅ 能 | ggml 全开源，算子可读、可测、可替换 |
| **NPU（RKLLM）** | ❌ 基本不能 | runtime 闭源，拿不到算子级 profile，没法替换实现 |

这个边界要在项目一开始就说清楚，否则「NPU 算子优化」会变成一句无法兑现的话。
RKLLM 那边能调的只有转换期的旋钮（量化方案、分组大小、上下文长度）
和运行期的少量参数（NPU 核数），这是**配置调优**，不是算子优化。

所以本仓库的算子工作全部落在 CPU 路径上。

## 优化目标不是「更少指令」

decode 阶段的 GEMV 算术强度约 2 ops/byte。A76 的平衡点（614 GOPS ÷ 34.1 GB/s）
约 18 ops/byte——差了将近一个数量级。

**结论：GEMV 是彻底的 memory-bound。** 优化目标是让访存流水打满，
而不是省指令。一个内核跑到接近实测 DRAM 带宽就到头了，此时再抠指令序列
不会更快。

这也是为什么 `kernels/bench_gemv` 把 GB/s 放在比耗时更显眼的位置：
GB/s 才能告诉你还有没有优化空间。

## 具体到 RK3588：只能用 SDOT

A76 是 Armv8.2-A，有 dotprod，**没有 i8mm 也没有 SVE**。

这一条排除掉了很多现成经验：

- llama.cpp 针对 i8mm（`SMMLA`）的 `Q4_0_8_8` 重排路径 → 走不到
- 各种基于 SVE 的 ARM LLM 优化 → 编不过
- Apple silicon / Neoverse 上的调优结论 → 不可移植

能用的是 `SDOT`：单条指令在 128-bit 向量上做 4 组 4-way 点积 = 16 次乘加。
两条 `SDOT` 吃掉一个 32 元素的 Q4_0 块。

编译时必须显式指定：

```
-march=armv8.2-a+dotprod+fp16 -mtune=cortex-a76
```

写 `native` 在交叉编译时无意义；写更高的架构等级会在板子上直接 SIGILL。

## 实现要点

`kernels/q4_gemv.c` 里的核心决策：

**一次处理 4 行。** 激活向量在 4 行之间复用，一次加载摊掉 4 倍开销；
寄存器用量（4 累加 + 2 激活 + 每行 2 权重）仍在 32 个 v 寄存器以内不会 spill。
8 行会 spill，预期反而更慢——**但这条还没在真机上验证**，上板后要扫一遍。

**fp16 转换走位运算而不是 `__fp16`。** 这样同一份代码在 x86 上能跑出
逐位一致的结果，NEON 版本才能用标量版本做正确性基准。
这个决定让下面这条验证成为可能。

## 当前验证状态

| 项 | 状态 |
| --- | --- |
| 标量参考实现（x86） | ✅ 通过 |
| NEON dotprod 编译 | ✅ 无警告，objdump 确认 `SDOT` 已生成 |
| NEON dotprod 数值正确性 | ✅ qemu-aarch64 下逐行比对，最大相对误差 `0.000e+00` |
| NEON dotprod 性能 | ❌ 未测，需要真板子 |
| 4 行分块是否最优 | ❌ 未测 |
| 与 llama.cpp 内建内核对比 | ❌ 未测 |

**qemu 下的耗时数字不要引用。** 它是功能模拟，跟真实硬件的时序没有任何关系。
qemu 能证明的只有一件事：这个内核算得对。

## 上板后要做的实验

按优先级：

1. **先测实际带宽**（`mbw` 或 STREAM）。没有这个数，所有 GB/s 都没有参照。
2. **内核 vs llama.cpp 内建实现。** 如果自己写的更慢，说明 ggml 已经做了
   本文没想到的优化，去读它的实现比继续调自己的更有价值。
3. **分块大小扫描**（2 / 4 / 8 行），验证或推翻上面的 spill 假设。
4. **线程数与绑核**：4 大核 vs 8 核混用 vs 只用小核。
5. **权重预取**：`PRLD`/`__builtin_prefetch` 提前拉下一块权重，
   看能不能把访存延迟藏进计算里。memory-bound 场景下这是少数还有空间的方向。

## 一个诚实的预期

考虑到 ggml 在 ARM 量化内核上已经打磨了很久，自己写的 GEMV **大概率跑不赢它**。
这个项目里写这个内核的价值不在于超过 llama.cpp，而在于：

- 亲手量出「离带宽上限还差多远」这个数；
- 搞清楚 RK3588 这块芯片上哪些优化手段是可行的、哪些是纸上谈兵；
- 有一个可控的实验对象，能干净地做单变量实验（分块、预取、布局），
  这在 llama.cpp 那个体量的代码库里很难做。

如果最后结论是「ggml 已经接近带宽上限，没有优化空间」——那也是一个有价值的结论，
而且比一个含糊的「优化了 x%」诚实得多。
